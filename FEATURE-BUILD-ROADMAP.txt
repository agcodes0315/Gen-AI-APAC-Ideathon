IMPORTANT ARCHITECTURE RULE
---------------------------
Do NOT implement the persistence-heavy features above against guessed Firestore
collection names or guessed notification preferences.

The following current files are required to build the entire 12-feature bundle
without risking auth, ownership isolation, notification opt-in, or provenance:

SERVER / DATA
- server/notificationService.ts
- server/emailService.ts
- server/perspectiveWatchProcessor.ts
- server/notificationRoutes.ts
- server/firestoreService.ts
- server.ts
- firestore.rules

CLIENT
- src/components/PushNotificationSettings.tsx
- src/components/JournalEditor.tsx
- src/components/JournalList.tsx
- src/components/DashboardOverview.tsx
- src/lib/api.ts
- src/types.ts

Once those current authoritative files are supplied, the complete bundle can be
implemented as one consistent patch rather than creating parallel storage systems.

WHY THIS MATTERS
----------------
MirrorTrace's product promise is owner-isolated data, consent-governed AI memory,
and traceable provenance. A localStorage-only implementation for favorites,
versions, decisions, assumptions, chains, or revisit reminders would technically
"work" but would violate that architecture by becoming device-only and disconnected
from the existing Firebase user namespace.

Likewise, a brand-new notification scheduler that guesses opt-in fields could
accidentally bypass existing push/email preferences.

So this pack fixes the calendar flash immediately and defines the exact safe path
for the full 12-feature implementation.
